# Kickoff — KICK-0002: Docker-native minimal-footprint refactor

- **Date**: 2026-07-25
- **Created by**: pm-orchestrator
- **Status**: pending Director approval

## Initiative

Docker-native minimal-footprint refactor

## Director brief (2026-07-25, verbatim intent)

1. The product is not practical enough: too much must still be downloaded. This
   project must run on an **external server**, most likely with a terminal as
   the only UI. The operator should install at most Docker, git, and trivial
   dependencies — nothing more.
2. We are not using what we already have: there is no Dockerfile, and we are
   not leaning on prebuilt, ready-to-run images.
3. Docker now ships its own way to run models. Research which is better: a
   self-hosted Ollama server vs Docker's own model tooling.
4. Running the `python3` scripts requires installing things; ideally the image
   already carries what we need.
5. Consider refactoring everything if Docker offers the better alternative.

## Baseline findings (evidence gathered before proposing)

Established by inspection of this repository at commit `23cd468`:

- **Serving already uses a prebuilt image.** `docker-compose.yml` and
  `templates/chat/docker-compose.yml.j2` run
  `ghcr.io/ggml-org/llama.cpp:server` pinned by digest. Point 2 is therefore
  only half true: the gap is that **the generator itself** (the Python CLI) has
  no image and no Dockerfile.
- **The Python runtime dependency is already minimal**: `requirements.txt` is
  `Jinja2` + `MarkupSafe`. The heavy install list (`requirements-dev.txt`:
  mypy, ruff, coverage, pip-audit) is developer/CI tooling, not operator
  tooling. So the operator's real Python burden is small but **non-zero and
  unmanaged** — it still needs a Python 3.10+, a pip install, and a
  working venv on the target server.
- **The genuinely heavy, unautomated download is the model weights.** Today the
  operator must source a `.gguf` by hand into `./models/<preset>.gguf`;
  `validate --tier host` and `wizard` only *check* that it exists. There is no
  supported pull path. This is the single largest practicality gap and it maps
  directly to the Director's point 1.
- Codebase size in scope for any refactor: ~1.3k lines of CLI/render/validator
  Python, ~0.4k lines of Jinja templates, ~1.7k lines of tests, plus one golden
  fixture workspace (`tests/golden/chat-ornith-medium-localhost/`).

External research (initial pass, to be deepened under TASK-R below):

- **Docker Model Runner (DMR)** works on plain Docker Engine on Linux (no
  Docker Desktop), exposes **OpenAI- and Ollama-compatible APIs**, and pulls
  models as **OCI artifacts** from Docker Hub / any OCI registry / Hugging
  Face. Backends: CPU, NVIDIA CUDA, AMD ROCm, Vulkan; vLLM backend for NVIDIA.
- **DMR's API is unauthenticated**: any client that can reach it — *including
  other containers on the same Docker network* — can pull, load and run models.
  This collides head-on with this project's fail-closed localhost posture and
  is the decisive security question for the choice.
- **Ollama** installs as a standalone daemon (`curl | sh`), has the larger
  model library, and is itself distributable as a container image — so it does
  not necessarily violate the "Docker only" constraint.
- The status quo (**pinned llama.cpp server image + generated Compose**) is the
  only one of the three that currently satisfies our hardening baseline
  (non-root, `cap_drop: ALL`, read-only rootfs, `127.0.0.1` bind, digest pin).

## Proposed plan

**Product thesis of the pivot**: the deliverable stops being "a Python
generator you install" and becomes "**a Docker image you run**". Operator
contract on a fresh external server:

```
git clone <repo> && cd ai-server
docker compose run --rm ai-server wizard      # or: docker run ... ai-server
```

Nothing else installed. No Python, no pip, no venv, no manual `.gguf` hunt.

Six phases. The Director has chosen correctness over speed (feedback point 3),
so we deliver one coherent refactor rather than partial drops.

- **Phase H — Host inspection (`doctor`).** New capability, from Director
  feedback point 2. A command that inspects the actual machine — CPU model and
  core count, total/available RAM, GPU vendor and VRAM (NVIDIA / AMD / Intel /
  Apple / none), free disk, Docker Engine version and available backends — and
  emits a **hardware tier**. Every downstream choice (preset, profile, runtime
  backend, context size, resource limits) is derived from that tier instead of
  being guessed by the operator. Runs on the target machine, works headless,
  and its output is a machine-readable artifact the generator consumes.
- **Phase R — Runtime decision (research + decision ceremony).** Engineering
  produces a written comparison of three options against fixed criteria:
  (a) status quo llama.cpp image + generated Compose, (b) Docker Model Runner,
  (c) Ollama in a container. Criteria: operator install footprint, model
  acquisition/pull path, access-control enforceability (now including LAN +
  bearer token, see Phase N), digest-pinnability and supply-chain
  auditability, GPU/CPU portability across hardware tiers from Phase H,
  resource limits (`mem_limit`, `cpus`, `pids_limit`), offline/air-gapped
  behaviour, and blast radius of DMR's unauthenticated-API property. The
  reference target is **a reused consumer laptop acting as a server**
  (Director feedback point 1), so integrated-GPU/Vulkan and CPU-only paths
  carry as much weight as CUDA. Output: recommendation + a `decision` ceremony
  record. **No refactor starts before this closes.**
- **Phase I — Generator image.** Add a `Dockerfile` for `ai_server_generator`
  (slim Python base, digest-pinned, non-root, deps baked in) and a root
  `compose.yml` service that runs `doctor|matrix|generate|validate|wizard`
  with the repo bind-mounted. Solves Director points 2 and 4. Existing CLI
  semantics and tests stay green.
- **Phase N — Network access and authentication (posture change).** The
  Director has explicitly authorized LAN exposure and bearer-token auth
  (2026-07-25). The repository's stated exit condition for this — "an
  authenticated TLS gateway that mechanically enforces a client allowlist" —
  therefore becomes the deliverable, not a blocker. Scope: a reverse-proxy /
  gateway container terminating TLS, bearer-token verification, client
  allowlist enforcement, `--access lan` and `--auth bearer-token` unblocked in
  the generator only when the gateway is present in the emitted workspace,
  token generation with correct file modes, and rotation guidance. **A bearer
  token over plaintext HTTP is not an acceptable intermediate state**: TLS and
  token ship together or neither ships. Localhost stays the default; LAN is
  opt-in and must be chosen explicitly.
- **Phase M — Model acquisition.** Implement the supported pull path chosen in
  Phase R so the operator never hand-places a `.gguf` again, with digest
  verification and an explicit offline mode. Model selection is filtered by
  the Phase H tier so an operator cannot pull weights the machine cannot run.
- **Phase X — Refactor.** Migrate templates/validator/golden fixtures to the
  chosen runtime and the new access model, keep or improve every hardening
  control, update README/docs/wiki, and provide a migration note for
  already-generated workspaces.

**Sequencing**: H and R run in parallel and are the only phases that start
immediately. I follows H (the image must ship `doctor`). N is designed in
parallel with R but implemented after it, since the gateway wraps whatever
runtime wins. M and X are gated on R. Nothing merges without Gate 1.

**Out of scope for this iteration** (Director decision, round 2): exposure to
the public internet and any router/port-forwarding configuration. Phase N
targets a trusted home/office LAN segment with per-client authorization.

## Per-area specifications (draft)

### Product (product-manager → product-analyst)

- Own the operator contract for the target user fixed in round 2 (entrepreneur
  / home worker / small dev team reusing an old machine, terminal-only, not a
  sysadmin). Acceptance test: *from `git clone` to a served response on a
  reused consumer laptop with only Docker + git installed*, and then reachable
  from a second machine on the same LAN with a token.
- Rewrite the README quick start around the container entry point; the
  `pip install -r requirements.txt` step must disappear from the operator path
  (it stays only in the contributor path).
- Define acceptance criteria for Phase R's comparison so the decision is made
  on evidence, not preference; own the WARN/NO-GO semantics if the runtime
  changes.
- Own the hardware-tier model from Phase H: define the tiers, and the mapping
  from tier → recommended preset/profile/context so `doctor` gives the operator
  a decision, not a datasheet.
- Own the LAN opt-in UX: choosing `--access lan` must be a deliberate,
  informed step with the risk stated in plain language at the moment of choice.

### Engineering (engineering-manager → ml-platform-engineer, ml-systems-engineer)

- **ml-platform-engineer** owns Phase I: `Dockerfile` (digest-pinned slim base,
  non-root user, `requirements.txt` baked, no build toolchain in the final
  layer), root `compose.yml` generator service, and CI build so the image is
  verified on every PR. Keeps the emitted-workspace scripts working unchanged.
- **ml-systems-engineer** owns Phase R: hands-on evaluation of DMR and Ollama
  on a Linux/Docker-Engine target, benchmarked against the existing llama.cpp
  baseline in `logs/benchmarks/`, plus Phase M's pull-and-verify path. Also
  owns Phase H's detection logic: it must degrade gracefully (unknown GPU,
  missing `/proc` fields, no `nvidia-smi`) and never fail the run because a
  probe was unavailable.
- Gate 1 (`.pm-harness/standards/GATES.md`) plus the existing suite
  (`scripts/ci.sh`, ruff, mypy, coverage ≥80%, golden fixtures) must stay green
  through every phase; golden fixtures are regenerated deliberately, never
  silently.
- Open question: minimum supported Docker Engine version, since DMR is
  version-gated and Compose `env_file: path:` syntax already constrains us.

### Security (security-engineer, under engineering-manager)

- **Owns Phase N.** The Director authorized LAN + bearer token on 2026-07-25;
  Security's job is now to build it correctly, not to refuse it. Deliverables:
  a threat model for the LAN posture, the TLS-terminating gateway, token
  generation/verification/rotation, client allowlist enforcement that is
  mechanically checked by `validate`, and updated README/runbook language
  replacing the current fail-closed statements. Non-negotiable: no bearer token
  is ever accepted over plaintext HTTP, and `validate` must fail closed if the
  emitted workspace claims LAN access without a working gateway.
- **Per-client access restriction is MVP scope** (Director, round 2): the
  operator must be able to decide which machines on their own LAN reach which
  models, via bearer tokens plus a gateway-enforced client allowlist. A trusted
  LAN is not an authorized LAN.
- Certificates: local/self-signed generated by the workspace, with a documented
  trust-the-cert step for the client. No public CA and no mTLS this iteration.
  Build the gateway so public exposure later is configuration and hardening,
  never a rewrite — in particular, do not assume clients share the subnet.
- Blocking review of Phase R with veto: DMR's unauthenticated API reachable by
  any container on the same network must be modelled explicitly (threat model +
  mitigation, e.g. dedicated network, no shared network with the model socket,
  or rejection of DMR outright). This weighs heavier now that LAN is in scope.
- Any new image must be digest-pinned and land in `sbom.json`; the existing
  `scripts/resolve_image_digest.sh` path is extended, not bypassed.
- Verify the generator image preserves the current controls: non-root,
  `no-new-privileges`, `cap_drop: ALL`, read-only rootfs where applicable, and
  that no credential is created or written anywhere.
- Model-pull integrity: checksum/digest verification is mandatory before a
  weights file is ever used.

### Design / UX (ux-dev, under engineering-manager)

- Terminal is the only UI. Own the one-command onboarding: error messages must
  say what to install and what to run next, with no Python traceback surfacing
  to the operator.
- Ensure `wizard` works identically inside the container, including the
  non-interactive path (no TTY → require flags, never block).

   it acts as a server."*
2. *"Depends on the machine's specifications. I think we should introduce an
   inspection of the machine or server and build from there, so we should have

Plus an unprompted directive:

### How each point was incorporated

1. **Docker-mandatory question deferred to evidence, target machine fixed.**
   The reference target is now explicitly a reused consumer laptop acting as a
   headless server. Phase R must weight integrated-GPU (Vulkan) and CPU-only
   paths as heavily as CUDA, and the Docker-vs-Python-path decision is folded
   into Phase R's recommendation rather than decided up front.
2. **New Phase H — host inspection.** A `doctor` command that profiles the
   actual machine and emits a hardware tier; presets/profiles/backends/limits
   are derived from that tier. This is the "several options" the Director
   asked for: options selected by the machine, not by the operator guessing.
3. **Sequencing changed from "ship Phase I first" to one coherent delivery.**
   The Director prefers a correct, complete result over an early partial one,
   so no phase ships as a standalone drop; Gate 1 applies throughout.
4. **Posture change accepted — new Phase N, owned by Security.** The Orchestrator
   flagged in session that the repository currently refuses `--access lan` and
   `--auth bearer-token` by design, with a documented exit condition ("an
   authenticated TLS gateway that mechanically enforces a client allowlist"),
   and that a bearer token over plaintext HTTP is worse than no token. The
   Director's instruction is therefore implemented as *building that exit
   condition*, not as removing the guard. TLS and token ship together.
   Localhost remains the default; LAN is explicit opt-in. Public-internet
   exposure remains out of scope pending a separate Director decision.

Answering the LAN trust-boundary question:

> *"Everything will point at a local network, home or office, trusted, but with

> have a modem from a local internet provider — not necessarily infrastructure
> to expose their ports."*
>
> *"That said, it will be easier for us to provide that configurability — but
> not in this iteration, unless it is part of a new MVP concept, Maximum
> Possible Value, that we can deliver in this iteration."*

### Target user (now a fixed product constraint)

Entrepreneurs, remote/home workers, and small development teams giving a second
life to hardware they would otherwise sell off. Implications the whole roster
inherits:

- The machine is **consumer hardware, heterogeneous, and often old**. Phase H's
  tiering is not a nicety — it is the feature that makes the product work at
  all for this audience, because the operator does not know what their machine
  can run.
- The operator is **technical enough to use a terminal but is not a sysadmin**.
  No step may assume network engineering, certificate authorities, or router
  configuration.
- The value proposition is *"the laptop I was going to sell now serves models to
  my home or office in one command"*. Every scope decision is judged against
  that sentence.

### Trust boundary — resolved

Trusted home/office LAN. Certificate strategy: local/self-signed, generated by
the workspace; no public CA, no mTLS in this iteration. On top of the trust
boundary, **per-client access restriction is in scope and is MVP-level value**:
bearer tokens plus a client allowlist enforced by the gateway, so the operator
can decide *which machines on their own LAN* may reach which models. "Trusted
LAN" means we assume the network is not hostile — it does not mean every device
on it is authorized.

### Public-internet exposure — decided out of this iteration

The Director opened the door to including it if it qualified as Maximum
Possible Value for this iteration. The Orchestrator's recommendation, accepted
as the working decision: **no.**

- The value jump for the target user completes entirely inside the LAN. Internet
  exposure adds no value to *"my old laptop serves my house or office"*.
- We cannot know the user's infrastructure: CGNAT, dynamic IPs, provider-locked
  modems and routers without port-forwarding are all common. A feature we cannot
  make work reliably generates support burden instead of value.
- It changes the threat model from "someone already on my network" to "the
  entire internet", which would demand a public CA, real certificate lifecycle,
  rate limiting, abuse handling, and audit logging — none of which fits this
  iteration.

Design constraint carried forward: Phase N's gateway must be built so that
adding public exposure later is a configuration and hardening exercise, not a
rewrite. It must not bake in the assumption that clients are on the same subnet.
