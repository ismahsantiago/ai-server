## Initiative
Local lightweight AI model lab

## Proposed plan
Objective: turn your Ryzen 5 + Radeon Vega + 12 GB RAM laptop into a practical local AI lab focused on lightweight model serving, quantized inference, and constrained fine-tuning workflows.

Phase 1 (Foundation, week 1): OS and driver baseline, Python + package manager, local model runners, reproducible project structure, observability basics, and smoke tests.

Phase 2 (Serving MVP, week 1-2): model catalog (small multilingual models + code assistants), API gateway (OpenAI-compatible local endpoint), presets per hardware profile, and benchmark matrix (latency, memory, quality).

Phase 3 (Fine-tuning lab, week 2-3): low-VRAM methods (LoRA/QLoRA where feasible), dataset ingestion and cleaning pipeline, experiment tracking, and rollback-safe model versioning.

Phase 4 (Operations and safety, week 3): security hardening for localhost/LAN exposure, artifact governance, backup/restore, repeatable update playbook, and quality gates.

Phase 5 (Expansion roadmap): optional distributed/offload setup, RAG workloads, multimodal experiments (within hardware limits), and migration path to stronger hardware or remote accelerators.

Milestones:
1) Reproducible local stack running one baseline model.
2) Stable local API service for at least two models.
3) First constrained fine-tuning run with logged metrics.
4) Hardened and documented lab operations.

## Per-area specifications (draft, one subsection per applicable area)

### Product (draft)
- Define the lab's first 3 use cases: chat assistant, coding copilot, and document Q&A.
- Prioritize "works reliably on 12 GB RAM" over raw model size.
- Success metrics: time-to-first-response, tokens/sec, crash-free session rate, and tuning cycle duration.
- Explicitly separate "production-like serving" vs "experimental tuning" workflows.
- Include acceptance criteria for each milestone (demo-able outcomes).
- Maintain a capability matrix: task type vs chosen model vs hardware footprint.
- Open questions: preferred language mix (ES/EN), target latency tolerance, and whether LAN access is required.

### Engineering (draft)
- Base runtime on lightweight, reproducible tooling (Python env + scripted setup).
- Prioritize quantized GGUF/4-bit model paths and CPU-first compatibility with optional iGPU acceleration.
- Provide one consistent local API surface (OpenAI-compatible proxy) to simplify clients.
- Add benchmark scripts for prompt throughput, cold-start, and memory envelope.
- Implement artifact folders: models/, datasets/, experiments/, logs/, backups/.
- Define strict resource budgets to avoid system lockups on 12 GB RAM.
- Open questions: preferred host OS details, willingness to use Docker, and storage partitioning strategy.

### Design (draft)
- Scope design to a minimal operator UX: CLI-first plus optional lightweight dashboard.
- Use clear status states: model loading, serving, tuning, failed, rollback-ready.
- Ensure one-command startup for common workflows.
- Provide concise runbooks and visual command cheatsheets.
- Favor readability and debugging speed over aesthetic complexity.
- Open questions: do you want only terminal UX or also a local web panel from day one?

### Security (draft)
- Default to localhost-only exposure; LAN access opt-in with explicit auth.
- Add secrets handling policy for API keys and private datasets.
- Require dependency/audit checks in Gate 1 before integration.
- Add data hygiene controls for fine-tuning inputs (PII and sensitive data checks).
- Keep signed checksums for model artifacts and backups.
- Define incident playbook for corrupted models or accidental external exposure.
- Open questions: any compliance constraints, and will third-party datasets be used?

### Data/Analytics (draft)
- Track benchmark and tuning metadata per run (model, quantization, params, hardware usage).
- Standardize experiment records to compare runs objectively.
- Keep simple local dashboards or markdown reports for trend analysis.
- Define data retention windows for logs and datasets to preserve disk space.
- Open questions: preferred tracking tool (lightweight file-based vs MLflow-like)?

### Support/Operations (draft)
- Create a daily health checklist: disk, RAM pressure, runner process health, and backup status.
- Provide troubleshooting matrix for OOM, model load failures, and degraded latency.
- Standardize update cadence for runtimes and model files.
- Keep rollback bundles for last-known-good serving setup.
- Open questions: desired backup frequency and acceptable downtime during upgrades.
