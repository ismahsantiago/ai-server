## Risks

- **Publishing tier names that later have to change.** A `tier_label` printed to an operator becomes a promise; a `tier_id` consumed by `doctor` and by a future Phase M pull filter becomes a contract. Renaming either after release breaks operator trust and strands any consumer keyed on the old identifier. Mitigation: todo 10 splits stable `tier_id` from renameable `tier_label` before either is published, and binds any change of the `tier_id` *set* to a `tier_model_version` bump plus a CHANGELOG entry. **Irreversible step**: the first release that prints a `tier_label` to an operator. Rollback: while TASK-0008 still emits `tier_model_status: "provisional-pending-product-signoff"`, no tier has been presented as authoritative, so the taxonomy can be replaced wholesale by editing `docs/hardware-tiers.md` and bumping `tier_model_version` from 1 — one document edit, no consumer stranded. After the first authoritative release, rollback costs a version bump plus a migration note, which is why todo 8's jargon check and todo 10's stability contract run *before* publication.
- **Ratifying or replacing the mapping while TASK-0008 is concurrently implementing it.** TASK-0008 is `started` and owns `ai_server_generator/tiering.py`. A verdict of `ADJUSTED`/`REPLACED` landing as an edit would collide with in-flight engineering work; landing as prose that engineering never reads would be a merge conflict of meaning rather than of text. Mitigation: this task writes **no** file under `ai_server_generator/` (todo 18 proves it mechanically); a non-`RATIFIED` verdict is expressed only as `### Specification for engineering` (todo 7) plus a routed delta list (todo 14). **Irreversible step**: none taken by this task. Rollback: the specification is inert until engineering acts on it; withdrawing it is deleting a section of a document this task owns.
- **Pre-empting the pending macOS engineering answer.** TASK-0008 is verifying whether a containerised Linux runtime on macOS is CPU-only, and TASK-0009 is investigating whether a host-side runner sidesteps it. A ruling written as an assertion becomes false the moment either answer lands the other way, and a false capability claim in the product's own tier document is exactly the failure this repository's honesty discipline exists to prevent. Mitigation: todo 13 requires the ruling to be *conditional*, with both branches fully specified and a stated selection rule, and its acceptance criterion mechanically rejects any unconditional macOS assertion outside a branch block. Rollback: when the engineering fact lands, the branch not selected is struck and the selected branch's text is promoted — a documented, expected edit, not a correction of a false claim.
