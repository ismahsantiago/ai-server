## Objective
Produce an actionable generator-first product and architecture plan for ai-server: a downloadable repository that generates configuration documents/files and exact launch commands for supported local AI server setups on a Linux laptop.

## Todos
- [x] Define the generator-first product model and AC: plan states user journey from git clone to generated config to server launch.
- [x] Define configuration families and AC: plan enumerates initial supported outputs for chat, coding, RAG, optional vision, LAN/localhost, and performance profiles.
- [x] Define generator architecture and AC: plan specifies inputs, templates, outputs, validation, and directory layout.
- [x] Define command UX and AC: plan lists proposed commands with examples and generated artifact paths.
- [x] Define implementation phases and AC: plan breaks work into sprint-sized tasks with acceptance criteria and gates.
- [x] Define quality/security controls and AC: plan includes validation, secrets/LAN safety, rollback, and test strategy.

## Gates
- `python3 .pm-harness/bin/harness.py validate`
- `python3 .pm-harness/bin/harness.py plan check TASK-0002`
- `python3 .pm-harness/bin/harness.py wiki check` (if wiki pages are touched)
- `test -f .pm-harness/HARNESS-SPEC.md`

## Risks
- Scope may expand into implementing the generator before the architecture is agreed; mitigate by keeping TASK-0002 plan-only and creating separate implementation tasks.
- Generated configurations could encode unsafe LAN exposure defaults; mitigate by making localhost the generated default and LAN opt-in require explicit auth/firewall variables.
- Too many model/config families can dilute Sprint 2; mitigate by defining MVP families first and deferring advanced variants.
- Hardware assumptions may be wrong without exact Linux distro/driver details; mitigate by designing generator profiles that declare prerequisites and validation checks.

## Open questions
- Should the generator be implemented first as Python CLI, shell scripts, or a hybrid? The plan should recommend one.
- What should be the first MVP model family: chat-first, coding-first, or a minimal shared baseline?
- Should generated files be committed examples only, or generated into an ignored `generated/` workspace by default?
- Should LAN auth default to static bearer token for MVP, with reverse proxy auth later?
