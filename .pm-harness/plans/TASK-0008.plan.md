## Objective
Deliver a `doctor` subcommand in `ai_server_generator` that, on every **supported**
platform — Linux host (primary), Linux inside the generator container, macOS on
Apple Silicon and macOS on Intel (both first-class deployment targets on
freshly reset machines) — with no TTY, no new runtime dependency and **no host
package installed by us**, exits 0 and produces two things: a human-readable
report on stdout, and a versioned machine-readable host profile at
`artifacts/host-profile.json` (`host_profile_version: 1`).

The report and the artifact keep **three** dimensions explicitly separate:

1. **Infrastructure resources** — what the machine physically has. Every fact
   carries `value`, `unit`, `status` (`measured` | `unknown` | `not-applicable`)
   and a `source` note stating how it was obtained. Determines *which models can
   run at all*.
2. **Software readiness** — whether the machine can execute a model *today*:
   Docker present **and its daemon reachable**, engine/compose versions read,
   GPU container runtime present where a GPU is claimed, free disk sufficient
   for the weights. **Presence is not readiness**, and the distinction is a
   reported product dimension, not an implementation detail. Every shortfall is
   emitted as a machine-readable **gap entry** (stable `gap_id`, `severity`, the
   fact that triggered it, and operator-actionable remediation text).
3. **Derived recommendations** — the provisional tier and the runnable/excluded
   preset partition, every entry quoting the literal measured inputs it used.

Windows is **out of scope**: `doctor` performs no probing on it, emits the
single blocking gap `platform.unsupported` pointing at the Linux
recommendation, and exits 0 (todo 2).

Three doctrines are binding on this task and on any task that inherits its
code; a later task may not trade them away without an amendment:

- **No probe may require installing anything on the host.** Only stock Linux
  (`/proc`, `/sys`) and stock macOS (`/usr/sbin/sysctl`, `/usr/bin/vm_stat`,
  `/usr/bin/sw_vers`, `/usr/sbin/system_profiler`) surfaces, or binaries
  already inside the Docker images this repository ships. `lscpu`, `dmidecode`,
  `hwinfo`, `nvtop` and every other add-on tool are **forbidden** — verified
  absent on both the aarch64 `python:3-slim` container and this macOS host. A
  probe that would need a host package it cannot assume degrades to `unknown`.
  Todo 21 enforces this mechanically with an `argv[0]` allowlist.
- **Assume a freshly formatted machine.** No accumulated state, no
  pre-installed developer tooling, no prior configuration by us.
- **The physical machine is the subject, not the process's sandbox.** Where the
  two differ — cgroup caps, and on macOS the Docker Desktop Linux VM sitting
  invisibly between the machine and the container — `doctor` says so instead of
  reporting the sandbox as the machine (todos 5 and 6).

The full per-platform capability contract is fixed in
`## Platform capability matrix` below; every degradation asserted there has a
named test in todo 18.

`doctor` is the **detect-and-tier front half of an adaptive install path**
(detect → tier → provision). It reports; it never installs, starts or
configures anything — the provisioning half belongs to a later task and depends
on TASK-0009's still-open runtime decision. The gap schema is designed so that
provisioning step consumes `software_readiness.gaps[]` directly, without
re-probing and without re-parsing prose.

The command must still exit 0 and emit a complete, all-`unknown` profile when
every probe fails, and the emitted tier must carry
`tier_model_status: "provisional-pending-product-signoff"` with its boundaries
computed at call time from the committed `ai_server_generator/presets.py`
contract fields rather than from hardcoded thresholds. Apple Silicon is a
**tiered configuration**, not a fallback branch: its tier is derived from
unified memory, so a Mac always receives a real tier and never sits at
`confidence: reduced` merely for being a Mac.

Verified by: `python3 -m
ai_server_generator doctor` exiting 0 on this repo's darwin/arm64 dev machine
with `memory.available_gb`, the Apple Silicon generation and the P/E core split
all `measured`; exiting 0 inside a stock `python:3-slim` Linux container under a
real cgroup v2 `memory.max`, discharged by todo 19 against the **now-reachable**
Docker daemon on this machine (verified 2026-07-25: `docker info` exits 0,
ServerVersion 29.6.1, context `desktop-linux`, Compose v5.3.0 — this reverses
the plan's earlier premise, see `## Open questions`); the artifact matching the
byte-exact schema fixture in `tests/test_doctor.py`; and every command under
`## Gates` exiting 0 with the pre-existing suite unmodified and green.

- [x] Add `ai_server_generator/readiness.py`, which turns facts into the **software readiness** dimension — a reported product dimension of its own, not an implementation detail of the infrastructure inventory. Infrastructure answers *which models this machine could run at all*; readiness answers *whether it can execute a model today*. **Presence is not readiness**: an installed Docker CLI with a dead daemon, an NVIDIA driver with no container toolkit, and a disk too small for the weights are all "installed" and none of them can serve a model. The module exports a frozen `Gap` dataclass and a single `GAP_REGISTRY: dict[str, GapSpec]` keyed by `gap_id`; `evaluate(profile) -> list[Gap]` is the only entry point and it derives every gap from facts already emitted — it runs no probe of its own. Entry shape: `gap_id` (stable, dotted, never renamed once shipped — it is the provisioning step's join key), `severity` in the closed set `blocking|degraded|advisory`, `title` (one operator-facing line), `triggered_by` (list of `{fact_key, observed_value}` copied literally from the profile, so the trigger is auditable without re-probing), `remediation` (`{"summary": str, "linux": str|None, "macos": str|None}` — the fix differs by platform and the operator must not have to guess which half applies to them), and `blocks` (list of capability strings this gap prevents, e.g. `["run-any-model"]`, `["gpu-acceleration"]`). Every string is written for a **non-sysadmin**: "Docker daemon unreachable" is a diagnosis, not a remediation; "Docker is installed but not running — start Docker Desktop, or run `sudo systemctl start docker` on Linux, then re-run this command" is a remediation. The registry ships exactly these fourteen ids: `platform.unsupported` (blocking); `docker.cli_missing` (blocking); `docker.daemon_unreachable` (blocking); `docker.compose_missing` (blocking); `docker.engine_version_unknown` (advisory); `gpu.driver_missing` (degraded); `gpu.container_runtime_missing` (degraded); `gpu.unreachable_from_container` (advisory); `memory.unobservable` (advisory); `memory.insufficient_for_any_preset` (blocking); `cgroup.limit_below_preset_requirement` (degraded); `execution.host_not_observable` (advisory); `disk.free_space_unknown` (advisory); `disk.insufficient_free_space` (blocking). Acceptance criterion: a test iterates `GAP_REGISTRY` and asserts, for **every** id without exception, that `severity` is in the closed set, that `remediation["summary"]` is non-empty and at least 40 characters, that at least one of the `linux`/`macos` keys is non-empty, that the summary contains no bare diagnosis without an imperative verb (asserted by requiring one of a committed imperative-verb list — `install`, `start`, `enable`, `free`, `re-run`, `increase`, `run` — to appear), and that the id matches `^[a-z_]+\.[a-z_]+$`; a second test asserts `set(GAP_REGISTRY) == set(<the fourteen literal ids>)` so adding one silently is impossible; a third drives `evaluate` over synthetic profiles covering each id's trigger and asserts the emitted `triggered_by` values are byte-equal to the profile's fact values; a fourth asserts `evaluate` on a fully healthy profile returns `[]`.

## Software readiness gap registry
Normative and stable. `gap_id` values are a published interface: once shipped
they are never renamed, only deprecated. Severity: `blocking` = no model can be
served today; `degraded` = a model can be served but not as well as the
hardware allows; `advisory` = the report itself is less certain. Remediation
text is written for a non-sysadmin and always states an action, never only a
diagnosis.

| --- | --- | --- | --- |

| `docker.cli_missing` | blocking | `docker.cli_present` false | Docker is not installed, and the server runs in Docker. On Linux, install Docker Engine with `curl -fsSL https://get.docker.com \| sh`; on macOS, install Docker Desktop from docker.com, open it once, then re-run this command. |

## Risks
- **False-confidence tiering on a machine we mis-measured.** A wrong RAM or VRAM read produces a tier that tells the operator to run a model their laptop cannot serve — worse than saying nothing, because this repository's credibility rests on not over-claiming (`_static_matrix_decision`, the `NOT VERIFIED:` lines in `cli.py`). Mitigation: every recommendation carries its literal measured inputs in `basis`; `confidence` drops to `reduced` and `undetermined_inputs` is populated whenever any input is `unknown`; an `unknown` RAM yields an empty `runnable_presets` with a stated reason instead of a fallback guess. Rollback: `doctor` is purely additive and touches no existing code path except registering a subparser — reverting the subparser registration and the four new modules restores the prior CLI exactly, and no pre-existing test is modified, so the revert is provably clean.
- **Container-vs-host mismeasurement.** Inside the generator image (Phase I) `/proc/meminfo` shows host RAM while the cgroup caps what the process may actually use; reporting either one as "the machine" is wrong. Mitigation: `execution.observation_scope` is a first-class fact, cgroup limits live under their own keys and are never merged into `memory.total_gb`, and the report prints an explicit `CONTAINER` block. Rollback: if the container path proves unreliable, ship `doctor` reporting `observation_scope: "container"` with the derived section suppressed and a note to re-run on the host — a one-branch change with no data-model change.
- **The invisible middle level: reporting a hypervisor's VM as the machine.** This is the sharpest edge found so far and it was measured, not theorised: inside `docker run --memory=2g` on this 16 GiB Mac, `/proc/meminfo` reports 7.75 GiB — the Docker Desktop Linux VM's RAM, which is neither the machine's 16 GiB nor the 2 GiB the process may use. A `doctor` shipped in the Phase I image would have reported 7.75 GB as the machine's RAM and tiered a supported platform wrongly, which is exactly the failure this task exists to prevent. Mitigation: todo 6 detects the VM boundary and **re-keys** the observations (`memory.vm_total_gb`, never `memory.total_gb`), so a consumer cannot read a VM number as a machine number even by accident; todo 19 proves it against the real hypervisor; todo 18 asserts the row. Rollback: if VM detection proves unreliable, invert the default — treat any `observation_scope != "host"` as machine-unobservable, which is strictly conservative and costs only precision on bare-metal Linux containers.
- **Remediation text that diagnoses instead of instructing.** The readiness dimension is worthless to its actual audience — an operator on a freshly formatted machine, not a sysadmin — if it emits "Docker daemon unreachable" and stops. This is a product failure that no type checker catches. Mitigation: the gap registry is a committed table in this plan, its remediation text is asserted non-empty, length-bounded and imperative-verb-bearing for **every** id by todo 10, and the renderer test asserts each emitted gap's remediation appears verbatim in stdout. Rollback: none needed — a weak string is a text change behind a single registry.
- **Readiness gaps drifting into prose that a provisioning step must re-parse.** `doctor` is the front half of detect → tier → provision; if the gaps ship as report text, the provisioning task re-derives them from facts and the two halves disagree the first time either changes. Mitigation: gaps are structured entries with a stable `gap_id` join key, a closed severity set, `triggered_by` quoting the literal fact values, and platform-keyed remediation; the human report is *rendered from* them, never the source of them. Rollback: the artifact is versioned, so a schema correction is a `host_profile_version` bump.
- **macOS probe fragility across releases.** `vm_stat` output and `sysctl` key names can change between macOS versions, and this plan now depends on both for `measured` facts on half the supported fleet. Mitigation: the page size is parsed from `vm_stat`'s own header rather than assumed (16384 here, 4096 on Intel), each `sysctl` key is read independently so one missing key degrades one fact rather than the probe, and every parse failure degrades to `unknown` — the same state the previous, unconditionally-degraded design shipped, so the downside is bounded by the old behaviour. Rollback: demote the affected fact to permanent `unknown` behind the seam; no data-model change.
- **Subprocess probes hang or the binary is absent.** `nvidia-smi` against a broken driver and `docker info` against an unreachable daemon are both realistic on a freshly formatted machine where Docker Desktop has been installed but never opened — the exact baseline this task assumes. (The daemon happens to be reachable on this dev machine today, so the unreachable case is proven by injected fixtures, not by convenience.) Mitigation: every subprocess goes through the single bounded `run_command` seam with an explicit timeout and total exception containment; `missing` is a normal result, not an error path; the timeout case has its own unit test. Rollback: lower the default timeout or demote the offending probe to a permanent `unknown` — both are one-line changes behind the seam.
- **Coverage regression from unmockable hardware paths.** Real hardware branches cannot execute in CI, so naive inline `open()`/`subprocess` calls would be dead lines dragging the build under the hard 80% gate. Mitigation: injection is a design constraint, not a testing afterthought — every probe takes `reader`/`runner`/`sysconf`/`disk_usage` parameters defaulting to the real implementations, so every branch is reachable from a synthetic fixture. Rollback: a genuinely unreachable path is deleted rather than excluded; no `# pragma: no cover` is added without naming it in an amendment.
- **Scope leaking into Phase R.** "Which backends are available" is one refactor away from "which runtime should we adopt", and TASK-0009 owns that decision. Mitigation: `probe_docker` emits an inventory with observation notes only, a test asserts the absence of runtime-preference strings in the module, and any benchmark, latency measurement or runtime comparison is an amendment request rather than a judgement call. Rollback: none needed — the guard is a review-time rejection, not a runtime state.
- **Tier semantics ship before product owns them.** KICK-0002 assigns tier definitions and the tier → preset/profile/context mapping to `product-manager`/`product-analyst`; shipping a tier product later redefines would silently change operator-facing advice. Mitigation: `tier_model_status: "provisional-pending-product-signoff"` and `tier_model_version` are emitted on every profile, and the boundaries are derived from committed preset data so a product redefinition becomes a data change, not a rewrite. Rollback: bump `tier_model_version` and replace the derivation function; the artifact is versioned and gitignored, so no consumer is stranded on an old shape.
- **Writing the artifact into a protected or committed location.** `generated/` is guarded by an ownership marker and `render.resolve_output_path`, and a committed machine-specific host profile would be both a privacy and a drift problem. Mitigation: the default target is `artifacts/host-profile.json` — already gitignored (`.gitignore` line 9) and already this repository's directory for machine-generated output (`scripts/ci.sh` writes `artifacts/coverage.xml` and `artifacts/pip-audit.json`) — and `doctor` never calls `resolve_output_path`. Rollback: `--no-write` already exists and deleting the file is non-destructive.
- **The host profile leaks identifying information.** CPU model, GPU name and disk paths identify a machine and the file is likely to be pasted into a support thread. Mitigation: the artifact carries no serial number, no hostname, no username-bearing absolute path beyond the models directory the operator chose, and it stays gitignored. Rollback: redact `gpu.name`/`cpu.model` to family-level strings if security review objects — a formatting change behind one function.
