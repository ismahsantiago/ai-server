# PM Harness pack/engine conformance findings require the pack owner

## Context

The technical audit (TASK-0007) raised four findings — ARN-001, ARN-002,
ARN-003, ARN-004 — against the installed PM Harness itself, not against the
`ai-server` product. Every other finding in that audit has now been remediated
or closed by an explicit Director decision. These four cannot be fixed here:
they live in the harness pack/engine that installed `.pm-harness/`, and
HARNESS-SPEC §12 forbids patching installed artifacts in isolation.

The four findings are:

- **ARN-001 (Alta)** — the manager contract pins OpenCode even though the same
  roster is materialized on Claude Code, so model id/provider/effort routing is
  wrong on at least one host.
- **ARN-002 (Alta)** — no Codex adapter exists, and the active catalog violates
  the OpenCode id format; the `gpt-5` used for the original audit came from a
  fallback that could not receive platform effort clamping.
- **ARN-003 (Media)** — native worker permissions are broad; the boundary that
  stops a worker delegating or writing into another agent's store is enforced
  only by prompt text, not by the adapter.
- **ARN-004 (Media)** — harness verification is local integration checking, not
  a versioned conformance suite for the installed engine (state machine, plans,
  checksums, memory, routing, migrations).

## Options

1. **Route to the pack/engine owner as a governed upgrade.** Correct per spec
   and fixes the findings for every project using the pack. Cost: depends on an
   external maintainer's timeline; the findings stay open meanwhile.
2. **Patch `.pm-harness/` locally.** Fast, but violates HARNESS-SPEC §12, is
   silently reverted by the next harness install/update, and makes this project
   diverge from the pack it claims to run.
3. **Accept and document the risk.** Zero effort. Defensible for a private
   single-operator project: the concrete blast radius is wrong model routing and
   weaker-than-declared worker isolation, with no external users exposed.

## pm-orchestrator recommendation

**Option 1 for ARN-001 and ARN-002, Option 3 for ARN-003 and ARN-004.**

ARN-001/ARN-002 cause real misbehavior today — work is routed to models that are
not the ones declared, which undermines every routing claim the harness makes.
They belong upstream and should be raised with the pack owner.

ARN-003/ARN-004 are hardening and assurance gaps. On a private, single-operator
project with no untrusted agents and no external users, the residual risk is
low, and accepting it explicitly is more honest than a local patch that the next
harness update erases. Revisit if this project ever gains additional operators.

## Director decision (2026-07-24)

Approved as recommended.

- **ARN-001, ARN-002** → routed to the pack/engine owner as a governed upstream
  change (Option 1). No local patch to `.pm-harness/` will be made; these stay
  open against the pack, not against this project.
- **ARN-003, ARN-004** → risk accepted and documented (Option 3). Justified by
  this being a private, single-operator project with no untrusted agents and no
  external users. To be revisited if additional operators are ever added.

State manifest `state/ESC-0001.json` transitioned to `closed`. This escalation
requires no further work in this repository.
