# ESC-0002 — The repository declares itself private and unlicensed, but the approved product is something users clone and run

## Context

KICK-0002 (approved 2026-07-25) redefines this product as software that
entrepreneurs, home workers, and small development teams will **clone onto their
own machines and run**: `git clone` then one `docker` command. The repository
currently contradicts that premise in writing. `pyproject.toml:10-15` states
*"Private project for personal use. It carries no license because it is not
[distributed] … If distribution is ever intended, a license and a third-party
notice review [are required]"*, and carries the classifier
`Private :: Do Not Upload`. There is no `LICENSE` file at the repository root.

This is not a new discovery. The TASK-0007 audit recorded it as finding
**LEG-001**, qualified, still `open`, with the note *"remains subject to the
Director's distribution decision"*. That decision was never put to the Director,
and it is the last genuinely unresolved item of TASK-0007 — which is why that
task is honestly still `in_progress` rather than merely un-ticked.

Without a license, recipients have no legal right to use, modify, or
redistribute the code. The `Private :: Do Not Upload` classifier additionally
blocks packaging and publication by design. Every phase now in flight — the
generator image, the LAN gateway, the model-acquisition path — is building
distribution machinery on top of an artifact that currently forbids
distribution.

## Options

- **Permissive open source (MIT or Apache-2.0).** Lowest friction for the target
  user and for adoption; Apache-2.0 additionally grants patent rights and is the
  safer choice if contributors ever arrive. Cost: irrevocable for released
  versions, and it permits commercial use by others without payment.
- **Copyleft (AGPL-3.0).** Keeps derivative works open, including
  network-served ones, which fits a product whose whole point is serving models
  over a network. Cost: a serious deterrent for company adoption, which cuts
  against the "small development teams" half of the target user.
- **Source-available / proprietary with a use grant.** Preserves future
  commercial optionality while still letting the target user run it legally.
  Cost: not open source, unfamiliar terms create friction and hesitation, and it
  complicates any future contribution.
- **Stay private and unlicensed, and narrow the product.** Internally coherent —
  but it contradicts the approved kickoff. If chosen, the target-user definition
  and the distribution premise must be revised, and several in-flight phases
  need re-scoping.

## pm-orchestrator recommendation

**Apache-2.0**, with `Private :: Do Not Upload` removed from `pyproject.toml`
and a `LICENSE` file added at the root.

Reasoning: the approved product is explicitly meant to be handed to people
outside this project, so an unlicensed repository is a defect, not a neutral
default. Among permissive options, Apache-2.0 costs nothing extra over MIT for
the user while adding an explicit patent grant and a contribution framework — a
cheap hedge for a project that intends to ship a security gateway and integrate
third-party inference runtimes. AGPL was considered and not recommended: its
network-copyleft trigger fits the architecture, but it would deter exactly the
small development teams the Director named as target users.

Two consequences to note whichever way this goes:

- The audit's own remediation note requires a **third-party notice review**
  before distribution. We vendor no code today, but we ship pinned upstream
  images (llama.cpp) and may add Docker Model Runner or Ollama in Phase R. That
  review belongs in whichever phase closes the runtime decision.
- Choosing anything other than "stay private" also settles what the generated
  workspaces are licensed under. Output produced by the generator should
  normally belong to the operator, not to us; the emitted templates should say
  so explicitly rather than leave it implied.

This is blocking in the sense that it should be decided before the product is
handed to anyone, not that it stops current engineering work. Phases H, R and
the tier model proceed regardless.

## Director decision — 2026-07-25

**Apache-2.0**, per the pm-orchestrator recommendation. Decided by the Director
in session on 2026-07-25 in response to this escalation.

Consequences to implement (tracked as TASK-0011):

1. Add `LICENSE` at the repository root containing the Apache License 2.0 text.
2. Remove the `Private :: Do Not Upload` classifier from `pyproject.toml` and
   replace the "private project for personal use, carries no license" comment
   at lines 10-15 with the actual license declaration and metadata.
3. Sweep README, docs, and templates for any remaining "private / not for
   distribution" language that now contradicts the licensed, clone-and-run
   product.
4. State explicitly what generated workspaces are licensed under. Output
   produced by the generator belongs to the operator, not to this project; the
   emitted templates must say so rather than leave it implied.
5. The third-party notice review required by the audit's own remediation note is
   **not** discharged here. We vendor no code today but ship a pinned upstream
   llama.cpp image and may add Docker Model Runner or Ollama in Phase R; the
   review belongs to whichever phase closes the runtime decision (TASK-0009).
   Carried forward explicitly so it is not lost.

With this decided, LEG-001 — the last genuinely unresolved item of TASK-0007 —
has a destination, and TASK-0007 can be closed once TASK-0011 lands.
